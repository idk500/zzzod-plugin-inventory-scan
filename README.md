# zzzod-plugin-inventory-scan

仓库扫描器 —— 绝区零一条龙插件：自动翻页扫描仓库中的代理人 / 驱动盘 / 音擎，OCR 识别并导出清单。

- 输出目录：`\.debug/inventory_exports`
- 安装：插件管理导入 zip，或待官方 plugin-data 收录后自动同步
- 许可：GPL-3.0（衍生自主仓）

## 驱动盘三应用职责边界（2026-10-28 拍板：维持三个独立应用）

扫描、标弃置、拆解是**三个互相独立的应用**，各自可单独触发、单独启停，
互相之间只通过游戏内状态（仓库余位 / 弃置标记）解耦协作，无代码级调用链：

| 应用 | app_id | 职责 | 不做什么 |
|---|---|---|---|
| 仓库扫描器 | `inventory_scan` | 翻页扫描仓库，OCR 导出清单（ZOD 格式 JSON） | 不标记、不拆解（清理节点已于 v1.1.0 移除） |
| 驱动盘清理标记 | `disc_cleanup`（本仓库第二个插件） | 逐盘判定并**打弃置标记**（可逆） | 不拆解；余位充足时整轮跳过 |
| 驱动盘拆解 | `drive_disc_dismantle`（框架内置应用） | 前往拆解画面，拆解**已弃置**的盘（也可切品质模式） | 不判定好坏，规格见下节 |

典型协作链路（手动按需串）：`disc_cleanup` 标记 → `drive_disc_dismantle` 拆解 →
`inventory_scan` 重扫对账。单应用反复触发方法见 `tools/elevated/SINGLE_APP_RUNBOOK.md`
（`-a/--app` 参数或 `run_app_once.ps1`）。

## 驱动盘清理标记（disc_cleanup）——判定规则 v2

与扫盘器解耦的独立应用（同仓库并列插件包，安装后各自出现在应用列表，可单独启停）。

**核心判定律（用户拍板）：套装效果需求 × 主词条错配 = 废盘**，而非主词条黑名单：

- 套装按效果分 4 类：输出（吃攻击/双暴）、异常（吃精通/异常积蓄）、击破（吃冲击力/失衡）、
  辅助防御（吃生命/防御/能量）；每类在 4/5/6 号位有各自的"死主词条"矩阵
  （1/2/3 号主词条固定，不参与判定）。例：双爆输出套装 × 防御主词条 = 废；
  其镜像同样成立（辅助套 × 攻击主词条 = 废）。
- R1：主词条 ∈ 该套装类型的死词条集合，且未装备、未满级（L15 永不自动标记）。
- R2：主词条有效但副词条潜力耗尽——仅 L12+ 且 4 条副词条全部为低价值（hp/def 系）。
  低级盘保留升级翻盘空间，不做副词条判定。
- 未知套装一律保留（fail-safe）并计数上报；争议口径（如异常套 6 号位 def_/hp_）按有效处理。
- 矩阵内置默认 + 支持配置文件 `config/disc_cleanup_rules.yml` 增量覆盖
  （set_type / dead_matrix / r2_min_level），新套装、新角色只改配置不动代码。
- 锁定盘不做视觉检测（后续可加锁按钮模板匹配）：游戏对锁定盘拒绝弃置操作，且弃置标记可逆。
- 指纹去重：执行时实时重扫仓库逐盘匹配，同指纹盘可互换，翻页重叠自动去重。
- 余位 ≥ `capacity_free_min`（默认 200）自动跳过整轮清理；弃置标记可逆，实际拆解由
  `drive_disc_dismantle` 应用执行（游戏单次拆解上限 300 件，存量大会自动分多轮）。
- 配置项：`probe_mode`（探测模式，只存样本绝不标记，默认开）、`mark_limit`（单轮标记上限）、
  `capacity_free_min`（余位门槛）。
- 依赖：需与 `inventory_scan` 插件同时安装（复用其驱动盘 OCR 解析模块）。

## 驱动盘拆解（drive_disc_dismantle）——运行规格书

> 应用本体在主仓 `src/zzz_od/application/drive_disc_dismantle/`，不在本插件仓库。本节记录它作为三应用之一的行为规格，
> 用于配置核对、排障和改动前对表。2026-10-29 对照代码与实跑日志核对。

### 1. 职责与边界

| 项 | 内容 |
|---|---|
| 一句话 | 把「已弃置」或「指定品质及以下」的驱动盘批量拆解成强化材料 |
| app_id | `drive_disc_dismantle`（框架内置应用，非插件） |
| 进一条龙链 | 是（`DEFAULT_GROUP=True`，`_group.yml` 里 `enabled: true` 才执行） |
| 单应用运行 | `OneDragon-Launcher.exe -a drive_disc_dismantle`（见 `tools/elevated/SINGLE_APP_RUNBOOK.md`） |
| 执行频次 | 每个游戏日 1 次：`config/01/app_run_record/drive_disc_dismantle.yml` 有当日记录即跳过 |
| 不做的事 | 不判定盘好坏（判据在 `disc_cleanup`）、不改弃置标记、不碰锁定盘、不碰已装备盘 |
| 可逆性 | **拆解不可逆**（盘消失、产出强化材料）；弃置标记本身可逆，真正销毁发生在本应用 |

### 2. 输入：两种选择模式（配置在 `config/01/one_dragon/drive_disc_dismantle.yml`）

| 配置项 | 取值 | 语义 |
|---|---|---|
| `dismantle_abandon` | `true` / `false`（默认 false） | `true` = 点「全选已弃置」，只拆**带弃置标记**的盘 |
| `dismantle_level` | `B` / `A及以下`（默认）/ `S及以下` | 仅 `dismantle_abandon=false` 时生效，点对应品质按钮，拆该品质及以下**未弃置**的盘 |

- 两项同时配置时以 `dismantle_abandon=true` 为准（代码先判弃置分支）。
- 品质按钮按游戏语义向下包含：选「S及以下」= B + A + S 全选。
- 本机日常配置：`dismantle_abandon: true` + `dismantle_level: S及以下`。弃置模式是推荐用法——好坏判定留在 `disc_cleanup`，
  拆解侧只执行「已经判定过的结果」，两个应用的责任边界不重叠。

### 3. 执行流程（12 个节点，失败边已标注）

| # | 节点 | 动作 | 边界处理 |
|---|---|---|---|
| 1 | 开始前返回 | 委托 `BackToNormalWorld` 回到大世界 | 入口幂等，任何界面进入都能起步 |
| 2 | 前往分解画面 | 导航到「仓库-驱动仓库-驱动盘拆解」 | 逐级点：菜单 → 仓库 → TAB-驱动盘 → 按钮-拆解 |
| 3 | 快速选择 | 点「按钮-快速选择」开筛选弹窗 | `success_wait=2`：弹窗动画未完成时后续点击会被吞 |
| 4 | 重置筛选 | 点「按钮-快速选择-重置」 | 本节点不做成功判定，点击后直接流转 |
| 5 | 选择弃置 | 弃置模式点「按钮-全选已弃置」；品质模式点「按钮-{品质}」 | — |
| 6 | 检查可拆数量 | OCR「文本-符合条件数量」读 N | N=0 → 等 1.5s 复查 → 仍 0 返回 `无可拆盘`；弹窗已自动关闭也判 `无可拆盘`；最多重试 5 次 |
| 7 | 快速选择确认 | 点「按钮-快速选择-确认」 | 成功边和失败边都接到节点 8 |
| 8 | 点击拆解 | 点「按钮-拆解」 | — |
| 9 | 点击拆解确认 | 点「按钮-拆解-确认」 | 失败边直达节点 11（可能没有需要拆的） |
| 10 | 确认获得 | 点「道具处理-获得」的「按钮-确认」 | 失败边直达节点 11 |
| 11 | 返回驱动仓库 | 有标题 → 点通用「返回」；无标题 → 先点「按钮-快速选择-关闭」关掉残留弹窗 | 最多重试 5 次；`无可拆盘` 状态也收口到这里 |
| 12 | 返回大世界 | 委托 `BackToNormalWorld` | 执行结束 |

### 4. 硬性约束（每条都是实机踩过的坑，改动前必读）

1. **顺序必须是「重置 → 选择 → 读数量」，不能颠倒。** 游戏会持久化快速选择弹窗上次的勾选状态，会话重启后
   「全选已弃置」丢失会让数量读数恒为 0（误跳过）；残留的未弃置区勾选还可能在确认时误选正常盘。重置后读数只反映
   本次点击，行为确定。
2. **快速选择点完必须等 2 秒再点弹窗内的按钮**（弹窗开启动画期间点击会被吞，2026-10-27 诊断出 0/300 选中）。
3. **数量读 0 不能立刻判跳过**：数量行刷新有异步延迟，等 1.5 秒复查一次，仍为 0 才判无可拆。
4. **数量行必须用多行 OCR**：`single_line` 会丢掉行尾的橙色数字，导致恒读 0。
5. **弹窗自动关闭 = 0 盘**：游戏在无可拆内容时会自己关掉弹窗，这时不要继续找「确认」按钮。
6. **无可拆盘时弹窗可能还开着**：返回节点必须先识别残留弹窗并点 X，否则会被挡住找不到标题。

### 5. 结果与运行记录

- 成功出口状态有二：正常拆解完成（返回画面状态名）、`无可拆盘`（`STATUS_NO_DISC`）。日志里靠状态名区分是否真的拆了东西。
- 运行记录写 `config/01/app_run_record/drive_disc_dismantle.yml`（`run_status` / `dt` / `run_time`）；当日再触发会被直接跳过。
- 通知：`NEED_NOTIFY=True`，`返回驱动仓库` 节点挂了「当前节点成功」通知。

### 6. 安全边界

| 边界 | 行为 |
|---|---|
| 单次上限 300 件 | 画面标题 `驱动盘拆解[n/300]` 是游戏硬上限；存量超过 300 需要多轮（换个游戏日，或手动单应用运行） |
| 锁定盘 | 游戏拒绝对锁定盘执行弃置，因此锁定盘根本不会带弃置标记；标记侧另有视觉锁定保护（匹配「开锁」图标，匹配不到一律按锁定跳过）做双保险 |
| 已装备盘 | 依赖游戏「显示已装备」开关默认 OFF，不在选择范围内——这是**外部前提**，不是代码保证 |
| 仓库余位门槛 | 拆解侧**不设**余位门槛。门槛（默认 200）在 `disc_cleanup` 侧，避免「为了腾空间反而误拆」 |
| 全量品质模式 | 若把 `dismantle_abandon` 关掉且选「S及以下」，等于拆掉所有未弃置低级盘，**没有标记环节兜底**——日常不要这么配 |

### 7. 三应用协作契约

- **唯一接口 = 游戏内弃置标记**：无代码级调用、无中间文件、无状态共享。
- 推荐顺序：`disc_cleanup` 标记 → `drive_disc_dismantle` 拆解 → `inventory_scan` 重扫对账。
- **幂等**：无弃置盘时整轮约 20 秒结束（实跑 2026-10-29 14:13:53 → 14:14:14），不点击拆解、不产生任何材料变化，重复触发无副作用。
- 顺序反了不会出错，只会白跑一轮（拆解先跑 → 本轮新标记的盘要等下次拆解）。

### 8. 观测与对账

- 日志关键字：`快速选择符合条件的驱动盘数量: N`（正常）/ `快速选择符合条件的驱动盘数量为 0 跳过拆解`（空转）。
- 诊断截图：`.debug/dismantle_debug/count_screen.png`（读数量瞬间的弹窗画面，专用于排查「标记了却读 0」）。
- 对账口径：拆解前后仓库标题余位数 + `inventory_scan` 重扫条数，两者差应等于本轮实际拆解量；
  单次拆到 300 时说明撞上限，需安排下一轮。

### 9. 已知限制

- 一次运行只拆一轮（受 300 上限），存量特别大时依赖多轮累积。
- 不统计产出材料、不校验拆解收益，只保证「按选择条件拆完」。
- 拆解确认弹窗（画面文档里的子态③）尚未建档（`docs/game/screens/驱动盘拆解.md` 标注「待补」）；
  游戏改动该弹窗时，须先补画面档案再改模板，不要凭截图猜坐标。

## 导出数据与配套优化器

「导出完整数据」会在输出目录生成 `inventory_<时间戳>.json`（ZOD 格式，dbVersion 2，含驱动盘 / 音擎 / 代理人清单）。导出前自动做全局指纹去重（翻页重叠不产生重复条目）。

该文件可直接导入在线配装优化器 **[Zenless Optimizer](https://zzz.233618.xyz/)**（绝区零优化器）：在「驱动盘」页导入 JSON，即可按角色 / 队伍计算最优驱动盘组合。推荐来自 @Usagi-wusaqi。
